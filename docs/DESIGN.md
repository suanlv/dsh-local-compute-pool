# 设计意图与边界

这份文档解释**为什么是这样设计的**，以及**它刻意不做什么**。想知道怎么用，看
[../README.md](../README.md)；想知道每个字段，看 [../plugin/README.md](../plugin/README.md)。

## 一句话

**它是本地推理的调度层：把"多个本地端点 + 每台机器只能同时服务几个请求"这个物理约束，
翻译成"把哪个子代理放到哪台机器、什么时候放、放不下时怎么办"的调度决策。**

## 为什么这一层必须存在

DSH 里本地模型本来就能用——`llm-pi-ai` 配好 provider 就行。问题不在"能不能连上"，
而在**引擎把模型看成一个逻辑端点，而本地服务真正的稀缺资源是容量**：
一个 `concurrency=1` 的 llama.cpp 收到两个并发请求，不是各慢一半，而是双双超时或显存爆掉。

DSH 没有请求级并发控制，所以两个 subagent 指向同一台机器时是硬撞。这个插件补的正是这一层缺失的语义：
**在"委派"和"发到线上"之间，插入一个知道容量、并且有权说不的东西。**

## 三层结构

| 层 | 回答的问题 | 机制 |
| --- | --- | --- |
| 触发白名单 `triggers` | **该不该接管** | 只有任务自身的模型跑在勾选的 provider 上，它的子代理才交给本地池 |
| 任务级预算 | **放几个** | 每个白名单 provider 带一个上限：写进该任务的提示词让模型知道该拆多宽，同时在流网关真实强制（跨机器算同一个任务的账） |
| 端点池 | **放哪台** | `active + reserved < concurrency` 才是候选；按负载铺开、一个子代理终身黏一台、失败冷却换机 |

三层共用同一个数字 `concurrency`，但回答的是三个不同的问题：能不能、几个、哪台。

## 三个机制各自对应一条物理约束

| 约束 | 机制 | 为什么必须是这个机制 |
| --- | --- | --- |
| 一次只能服务一个会话 | 每端点闸门 + 有界队列 | 并发不是"更快"，是"更坏"；宁可排队也不要打崩服务 |
| 上下文缓存能力弱 | 子代理**终身黏一台** | 每换一次机器前缀缓存全部作废，还要重放。黏性不是优化，是正确性 |
| 不擅长多发并行 | `least-busy` 铺开 | 多台机器的意义就是别让它们串在同一队里 |

## 三个容易误读的设计决定

**① 为什么任务自身的请求要占一个名额（`reserved`）。**
白名单与端点池指向同一个 provider 时，任务自己就跑在那台机器上。如果子代理也被分到同一台，
这台单槽服务端会同时收到两个并发请求——正是要避免的情况。所以任务自身的请求会占住该端点的一个名额，
子代理被分到别的端点；池里只有这一台时，子代理**保持继承线路、由服务端自身串行**，
而不是被塞进一个并不存在的第二名额。

**② 为什么粘性是写死的、不可配置。**
`sticky` 曾经是配置项，后来移除了：关掉它会让同一个子代理的**每次请求都重新选机器**
（还随内部游标轮转），前缀缓存反复失效、工具调用方言抖动、每次重新过闸门。
没有一个场景需要这个行为，留着只制造误操作的机会。

**③ 为什么"轮询"不再是策略。**
`least-busy` 已经包含轮换语义（含队列压力与平局轮转），有空闲端点时二者等价；单端点时三种策略完全相同。
真正的选择只有「铺开」对「固定第一台」。旧配置里的 `round-robin` 会被映射为 `least-busy`，不会报错。

## 刻意不做的事

* **不提供本地推理能力**。一个 HTTP 请求都不发（唯一的例外是 `local_pool` 的 `probe` 探活）。
  它不新增 provider、不改 baseURL、不管认证。
* **不认识"设备"**。它眼里只有配置里的 provider id；当前所有端点都是 `127.0.0.1` 形态，
  远端那台靠端口转发/隧道到达。**它不区分"同一台机器的两个端口"与"两台机器"**，
  也没有设备发现、远端传输、集群成员或认证。这也是它名字里没有"多设备"的原因。
* **不做重试**。重试归 `dsh-llm-retry`；换机能力恰恰**依赖**重试会重新经过 `agent/request`。
* **不做跨机协作**。没有会话迁移、没有跨机缓存共享、没有分布式状态。每个子代理的世界就是它黏住的那台机器。
* **不是通用负载均衡**。决策粒度是"子代理"，不是"请求"；请求级只会重新贴合既有分配。

## 已知的实现取舍

* **两份队列实现**（端点队列与任务预算队列）是同一个算法的两次实现，约 90 行重复。
  它们目前都对，合并需要引入统一的槽位队列原语（抽象本身有出错风险）。
  触发合并的条件：① 继续扩展（优先级/抢占/按主机分组）；② 需要第三次改动队列语义。
* **`concurrency` 是人工声明值**，插件无法探知服务端真实并发能力。填大了会把本地服务压垮。
  默认取 1 是保守选择。
* **`agent/request` 可能被调用两次**（插件根监听器 + agent 作用域监听器）。路由因此必须是幂等的：
  先认自己上一次的决定，命中就直接返回。这不是理论问题——曾经因此让同一子代理在两台机器间来回搬。
* **`Switch` 控件必须定义在模块作用域**。定义在组件内部会让 React 每次渲染都产生新的类型身份，
  从而卸载重建整棵子树（焦点丢失、动画重启）。测试桩把函数组件当普通函数调用，**测不出这类问题**。
* **设置页的 `Config` 依赖从 app.asar 导入 schemastery**。纯 Node 读不了 asar，所以用纯 Node 跑
  `tools/verify-install.mjs` 时 `Config` 那条会失败——那是检查工具的限制，不是插件的缺陷
  （`tools/probe-asar-import.mjs` 专门把这个差别演示出来）。
